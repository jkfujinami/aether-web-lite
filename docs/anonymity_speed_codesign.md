# Fetch 側の匿名性と速度の同時設計

> 前提文書

v4 で Publish 側 (誰が書いたか) は塞いだ。この文書は **Fetch 側 (誰が持っていて、
誰が読んでいるか)** を扱う。結論を先に書く:

> **匿名性を上げると速くなる構成が存在する。** トレードオフだと思っていたのは、
> 「読みたくなってから取りに行く」という時間軸を疑っていなかったからだった。

## 1. 前提条件 — 動かせないもの

### 1.1 環境制約

| # | 制約 | 帰結 |
|---|---|---|
| C1 | ブラウザピア。listening socket が無い | **アドレスで相手に届けられない。** 経路は既存の DataChannel の上にしか引けない |
| C2 | 新規接続 = signaling + ICE + DTLS | **1〜3 秒。** Tor が任意のリレーへ 100ms で TCP する世界とは別物 |
| C3 | 既存 DataChannel 上の 1 ホップ = 30〜80ms (同一地域) / 150〜250ms (越境) | **ホップを足すのは安い** |
| C4 | 直接隣人は IP を見る | 消せない (v4 §9-1)。隠せるのは「その IP が何を持っているか」だけ |
| C5 | 投稿者はオフラインになる | 保管は他人が肩代わりする必要がある (BBS のセマンティクス) |
| C6 | 母数が小さい | 匿名性は群衆の性質。10 ノード未満では何をやってもゼロ |

### 1.2 ★ 決定的な非対称性

**C2 と C3 の差が 20〜100 倍ある。**

これが設計の中心。Tor は「リレーを増やす = 新規 TCP を増やす」なので多段化が高い。
こちらは **既に張ってある接続を余分に辿るだけなら、ほぼタダ**。
つまり *この環境では多段化が Tor より安く、新規経路構築が Tor より高い*。

設計は「ホップ数をケチる」方向ではなく、
**「既存の接続グラフの上で何段でも回す。ただし新しい相手には繋がない」** に寄せる。

### 1.3 現状の資産

```
nonce       = randombytes_buf(32)             HintCrypto.ts:175  ← 板の鍵と無関係
mailbox_key = SHA256(nonce)                   HintCrypto.ts:166
placement   = hashToPosition(mailbox_key)     DHTMailbox.ts:84   ← 実質ランダム
position    = SHA256("AETHER/v3/position"‖peerId)  RingPosition.ts:38 ← 純粋関数
```

- **Broadcast Veil** — 全ノードが全 Hint を無条件に中継する。索引配布は既に flood 規模の
  帯域に耐えている。これは後で効いてくる資産
- **SlotBlob** — `u32be(hintLen) ‖ hint ‖ body`。本体と索引が同じバイト列に同居している
- **`fetchBody` のローカルヒット短絡** — 手元にあれば GET を出さない
  (`SchrodingerMailbox.ts:217`)。**0 パケット = 0 漏洩 = 0 レイテンシ**
- **DandelionRouter** — Stem/Fluff の機構が既にある (`FLUFF_PROBABILITY = 0.3`、ホップ
  カウンタ無し)。GET 側に転用できる

## 2. 何を濃くするのか

### 2.1 破らなければならない 3 つの連結

| | 関係 | 現状 |
|---|---|---|
| **L1** | 投稿者 ⟷ 投稿 | v4 で対処済 (Dandelion++ Stem + Hint 放流の時間分離) |
| **L2** | 保管者 ⟷ 内容 | **破れている** |
| **L3** | 読者 ⟷ 内容 | **破れている** |

### 2.2 攻撃者クラス

| | 能力 |
|---|---|
| T1 | 板の鍵を持つ。受動的に観測するだけ |
| T2 | T1 + 数ノードを立て、任意の相手に接続を張れる |
| T3 | T2 + PoW を投じて座標をグラインドし、狙った位置に着席できる (§18.5.3) |
| T4 | 大域受動盗聴 — **常に SCOPE 外**。P2P である以上どうにもならない |

### 2.3 今の穴は 1 本の線から来ている

```
board key ─→ Hint 開封 ─→ nonce ─→ mailbox_key ─→ position ─→ 担当 peerId 集合
```

`findKNearest` は距離ソートするだけ (`DHTMailbox.ts:96`)。position は peerId の純粋関数、
peerId は PEX で配り放題、Hint は Broadcast Veil で全員に届く。

したがって **T1 が、パケットを 1 本も出さずに、オフラインで
「どの投稿をどの peerId が保管しているか」を全件計算できる。** これが L2 の破れ。

同じ線が L3 も破る。`DhtGet { topic_hash }` は平文で、topic_hash = mailbox_key。
T3 は狙った投稿の mailbox_key 近傍に着席すれば、**その投稿を読みに来た IP を収穫できる。**
「この投稿を誰が読んだか」は令状の形をしている。L2 より重い可能性がある。

> **穴は 2 つに見えて 1 つ。** Hint の平文が「在り処」を含んでいることと、
> 在り処が公開の純粋関数で担当者に写ることの組み合わせ。

## 3. 使える手法と、この環境での値段

| | 手法 | L2 | L3 | レイテンシ代 | 帯域/容量代 |
|---|---|---|---|---|---|
| T-a | hop-by-hop 転送 GET + 逆経路応答 (Freenet) | ◎ | ○ | h×RTT (**安い**, C3) | 小 |
| T-b | 経路上キャッシュ | ◎ | — | **負** (以後ローカルヒット) | 中 |
| T-c | 秘密配置 + rendezvous (Tor onion service) | ◎ | ○ | 探索が routing→flood になる | 中 |
| T-d | GET の Stem 化 (既存 Dandelion 転用) | — | ◎ | 1〜3 ホップ | ほぼ 0 |
| T-e | **Hint 到着時の先読み** | ○ | ◎ | **負** | 中 |
| T-f | カバー複製 (復号できない Slot をランダムに引く) | ◎ | ○ | 0 (背景) | 大 |

各項の中身:

**T-a** 要求者は直接隣人としか喋らない。応答は逆経路で返る。**答えたのが隣人自身か
転送先か、要求者には区別できない。** これが無いと、仲介を何段挟んでも最後の一本が
「C が答えた」という事実を残す。**あらゆる構成の土台。**

**T-b** GET の応答を経路上の全ノードが保管する。**「持っている」が何も含意しなくなる。**
Freenet で保持者が問題にならない理由の本体。しかも 2 回目以降はローカルヒットで
**0 パケット**になるので、レイテンシは負。

**T-c** user 提案の「秘密の座標」。Hint の平文から在り処を外し、保管者 C 自身が選んだ
仲介 B に不透明トークンで登録する。**C が B を選ぶ点が決定的** — 座標由来で B を決めると
T3 がグラインドして着席できるが、C が選べば刺さらない。
代償: **鍵で経路を引けなくなる** ので探索が flood/random-walk になる。

**T-d** GET を Fluff する前に Stem に載せる。第 1 ホップに「こいつが発信源か転送か」を
区別させない。`DandelionRouter.publishVia` が payload 非依存に書いてあるのでほぼ流用できる。

**T-e** 後述。この設計の要。

**T-f** 復号できない Slot をランダムに引いて持つ。保持分布が「興味」と無関係になる。
帯域が青天井なので必ず上限が要る。

## 4. ★ 時間軸をずらす — 問題を作り替える

ここが本題。

現状は **「ユーザがスレを開く → GET を撃つ → 待たせる」**。だから
レイテンシ予算が数百 ms しかなく、そこに匿名化を積むと体感が壊れる。
「匿名性 vs 速度」に見えていたのはこの前提のせい。

しかし **Hint は Broadcast Veil で既に全員へ届いている。**
購読者は「本体が存在すること」を、読みたくなるより前に知っている。

> **索引の到着時点で本体を背景で引いておけば、読む時点では必ずローカルヒットになる。**
> `fetchBody` は既にローカルヒットで短絡する — **0 パケット、0 ms、0 漏洩。**

この 1 手で予算が変わる:

| | 予算 |
|---|---|
| 読んでから取りに行く | **200〜500 ms** — 匿名化を積む余地なし |
| 索引が来た時点で取りに行く | **10〜60 秒** — 5 ホップでも混ぜても遅延しても誰も気付かない |

**「速い匿名探索」という難しい問題が、「遅くていい匿名先読み」という易しい問題に変わる。**
T-a / T-c / T-d / T-f のコストは、ここに隠れて消える。

### 4.1 大きいファイルはどうなるか

先読みは本文 (数 KB) には効くが、ファイル共有では帯域が死ぬ。
ただし **ファイルは転送自体が数秒〜数分かかる。** 5 ホップの往復オーバーヘッドは
転送時間の数 % にしかならない。

> **レイテンシ問題は小さいオブジェクト固有の問題で、
> 小さいオブジェクトはまさに先読みできるもの。**
> 大きいものは元々遅いので多段化の代金を払える。**両方とも解ける。**

| | 小 (本文 数KB) | 大 (ファイル 数MB〜) |
|---|---|---|
| 取得 | 索引到着時に先読み | 要求時にオンデマンド |
| 体感 | 0 ms (ローカルヒット) | 転送時間が支配 |
| 匿名化予算 | 数十秒 | 転送時間の数 % |

## 5. 組み合わせ

### 5.1 二つの思想と、その選択

| | 保管者 | 可用性 | 経路 |
|---|---|---|---|
| **Freenet 型** (T-a+T-b) | 計算できるが**持っていることが無意味** | 高い。保管者が消えても残る | 鍵で引ける = 速い |
| **Tor 型** (T-c) | **誰が持っているか計算できない** | 保管者の生存に依存 | 鍵で引けない = 探索が要る |

★ **重要な観察: Freenet 型だけで、オフライン計算攻撃 (§2.3) は無力化する。**

T1 の計算結果は「peerId X が *担当* である」までしか言えない。経路上キャッシュが
普遍化すると **担当 ≠ 保持** になり、hop-by-hop 逆経路応答があると
**保持を確認できない** (X が持っていたのか転送したのか区別できない)。

つまり T-c (秘密配置) は **経路の引ける性質を捨てる代わりに得るものが少ない。**
「担当であること自体が不都合」と判断した場合の第二段に置く。

### 5.2 採用する層

```
Layer 0  時間軸のずらし        T-e   ← これが他の全部の代金を払う
Layer 1  保管を無意味にする    T-b (+ T-f)
Layer 2  要求を辿れなくする    T-a + T-d
Layer 3  速度を戻す            ローカルヒット短絡 (実装済) + 先読み
--------------------------------------------------------------
Layer 4  在り処を隠す          T-c   ← 保留。Layer 1 が効かないと判断した時のみ
```

Layer 1 と Layer 4 は **わざと冗長**。壊す攻撃者が違う。
Layer 1 は「持っている意味」を壊し、Layer 4 は「誰が持っているか」を壊す。

### 5.3 各連結がどう切れるか

**L2 (保管者 ⟷ 内容)**
- T-b + T-f で保持分布が担当集合と無関係になる → *担当* の計算に証拠価値が無くなる
- T-a で「X が答えた」が「X が持っていた」を意味しなくなる
- 保管者は依然として中身を読めない (Schrödinger は無傷)

**L3 (読者 ⟷ 内容)**
- T-e で読み取り時に GET が出ない。**観測点そのものが消える**のが一番強い
- 冷えたミス時は T-d が第 1 ホップから発信源を隠し、T-a が経路を切る
- T3 が狙った投稿の近傍に着席しても、来るのは転送された要求で、発信源ではない

**L1 (投稿者 ⟷ 投稿)** — v4 のまま。ただし T-b が副作用で効く。
本体を持っている者が増えるほど「最初に持っていた者」が薄まる。

## 6. レイテンシ収支

| 経路 | 現状 | 提案後 |
|---|---|---|
| 温 (先読み済み) | — | **0 ms / 0 パケット** |
| 温 (今のローカルヒット) | 0 ms | 0 ms |
| 冷ミス | RTT + 300ms grace ≈ 350〜550 ms | (2h+2)×RTT ≈ 300〜900 ms (h=3) |
| 全滅 | 4000 ms (ハードタイムアウト) | 同等 |
| 大ファイル | 転送時間 | 転送時間 × 1.05 程度 |

**定常状態では現状より速い。** 遅くなるのは「キャッシュより古い投稿を掘る」時だけで、
それは今も grace とタイムアウトで遅い。

## 7. 何が壊れるか — 正直な一覧

| | 問題 | 対処 |
|---|---|---|
| P1 | 先読みの帯域・容量が青天井 | 本文のみ先読み。ファイルは対象外。LRU 上限 |
| P2 | **購読者しか Hint を開けない → 先読みしたことが購読の証拠** | 先読みは T-a 経由で発信源が隠れている + T-f で復号できない Slot も引く |
| P3 | 逆経路の状態 (reqId → 前ホップ) がメモリと DoS 面になる | 上限 + TTL。Stem の再送機構と同じ扱い |
| P4 | GET のループ | reqId で重複排除。**reqId は要求ごとの乱数で内容と紐づかない**ので、Stem と違って oracle にならない |
| P5 | **GET に平文 TTL を載せると発信元が割れる** (Stem と同じ罠) | ホップカウンタを持たず確率で打ち切る。ただし到達性が要るので Freenet 式に「鍵に近づいたか」で継続判断する |
| P6 | 仲介 B が板の鍵も持つと L2 が復活 (T-c を採る場合) | 多段化 = 本物の onion 層。Layer 4 の話 |
| P7 | 母数 | 10 ノード未満では全部無意味。**閾値未満では素直に劣化させる** (v4 の `HintReleaseScheduler` と同じ思想) |

### P5 について

Stem では「ホップカウンタを平文で載せると上限値が発信元しか出せない値になる」ため
カウンタを全廃し確率停止にした (`messages.rs:69`)。GET でも同じ罠がある。

ただし GET は **届かなければ意味が無い** ので、純粋な確率停止では駄目。
Freenet は HTL を最大値付近と 0 付近で確率的に減らすことで
「最大値 = 発信元」を壊している。同じ手が使える。

## 8. 実装順序

効果 ÷ コストの順。**上 2 つは匿名性を上げながら速度も上げる。**

| # | やること | 効く連結 | 速度 |
|---|---|---|---|
| 1 | **Hint 到着時の本文先読み** (`SchrodingerMailbox.onOpened` → 遅延付きで `fetchBody`) | L3 | **上がる** |
| 2 | **GET 応答の経路上キャッシュ** | L2 | **上がる** |
| 3 | **GET の hop-by-hop 転送 + 逆経路応答** (`DhtGet`/`DhtRes` を転送型に) | L2, L3 | 冷ミスのみ悪化 |
| 4 | **GET の Stem 化** (既存 `DandelionRouter` 転用) | L3 | ほぼ 0 |
| 5 | **カバー複製** (帯域上限付き) | L2 | 0 |
| 6 | (保留) 秘密配置 + rendezvous | L2 | 探索コスト増 |

1 と 2 だけで **L3 の主要な観測点が消え、L2 の「担当 = 保持」が崩れる。**
しかも体感は速くなる。ここから入るのが正しい。

3 は `DhtGet`/`DhtRes` のワイヤ変更を伴うので TS/Rust 両方 + 相互運用ベクタ。
v4 §8.5 の教訓どおり、**ノードを跨いだ e2e テストを先に書く。**

## 9. 未解決 / この設計でも残るもの

- **C4 (直接隣人への IP 露出)** — 変わらない。変わるのは「その IP が何を持ち何を読んだか」
- **交差攻撃** — トリップが投稿をまたぐ永続識別子である限り、製品機能として攻撃入力を供給し続ける
- **シグナリングトラッカー** — 単一の令状執行先。分散化で希釈できるが消えない
- **母数** — コードの性質ではない
- **T4 (大域受動盗聴)** — 常に SCOPE 外
